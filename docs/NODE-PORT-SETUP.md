# إعداد المنافذ على الـNode

كيف تُشغَّل منافذ اتصال العملاء فعلياً: من تخصيص الـAPI إلى منفذ على الإنترنت.

هذا هو الملف الذي تحتاجه عندما يقول عميل «عنوان السيرفر لا يعمل» — أو قبل أن
تقولها أنت.

---

## 1. الصورة العامة

```
عميل ←── الإنترنت ──→ جدار المزوّد ──→ المضيف:PUBLISHED_PORT
                                              │
                                    docker-proxy / DNAT
                                              │
                                   container_ip:CONTAINER_PORT
                                              │
                                    عملية العميل (process.env.PORT)
```

النقطة التي تُنسى عادةً:Docker ينشر المنفذ بشكل صحيح، والعملية لا تستمع على
`CONTAINER_PORT`، فيبدو كل شيء صحيحاً من الخارج ولا يستجيب أحد.

هذه هي الحالة التي يفحصها `GET /servers/:id/ports` ويعرضها في لوحة التحكم
كخمس حقائق مستقلة.

---

## 2. نطاقات المنافذ

| أين | القيمة الافتراضية | ملاحظات |
|---|---|---|
| المنصة (`PORT_RANGE_FROM` / `PORT_RANGE_TO`) | `20000`–`32000` | يُقرأ عند الإقلاع؛ قيمة خاطئة تمنع الإقلاع |
| لكل نود (`nodes.port_range_from` / `port_range_to`) | `NULL` = افتراضي المنصة | تُضبط من **Admin → Nodes → Set port range** |

### لماذا ينتهي النطاق عند 32000؟

لينكس يستخدم `net.ipv4.ip_local_port_range` (الافتراضي `32768`–`60999`) كـ
**منفذ مصدر** لكل اتصال صادر. لو وضعنا مستمعاً داخل ذلك النطاق لتصادم مع
حركة المضيف نفسه، وظهر للمستخدم انقطاع متقطّع لمنافذ لا يشغلها أحد.

تحقّق على المضيف:

```sh
cat /proc/sys/net/ipv4/ip_local_port_range
```

إذا كانت قيمتك مختلفة، عدّل النطاق ليبقى تحتها. كل نطاق يُرفض إن كان:

| السبب | متى |
|---|---|
| `privileged` | حدّ أقل من 1024 |
| `inverted` | `from > to` |
| `too_small` | أقل من 64 منفذاً صالحاً |
| `overlaps_ephemeral` | يتقاطع مع `32768`–`60999` |
| `overlaps_other_node` | نودان على نفس المضيف |

## 3. الـDNS

كل نود يحتاج سجلّاً يشير إلى **عنوانه العام**:

```
node.hosting.troxe.dev.  A  203.0.113.10
```

هذا ما يعرضه `nodes.public_host` على العملاء. لا يوجد توليد سجلّ لكل بورت،
ولا يوجد أيّ Proxy في المسار: العميل يتصل مباشرة بالمضيف.

للتحقّق:

```sh
dig +short node.hosting.troxe.dev     # يجب أن يعيد IP المضيف
```

إذا لم يُعَد عنوان، أو أعاد عنواناً داخلياً (`10.x` / `192.168.x` / `172.16-31.x`)،
فلا تعرض العنوان للعملاء — اضبط `public_host` أولاً.

### تحذير: Cloudflare

**Cloudflare لا يمرّر المنافذ غير المدعومة على النطاق البرتقالي.** البورتات
المخصصة (`20000`–`32000`) غير مدعومة إطلاقاً، والقواعد المجانية المدعومة
(`80`, `443`, `8080`, `2052`, `2053`, `2082`, `2083`, `2086`, `2087`, `2095`,
`2096`, `8443`) محدودة、数量 منها مشترك مع موقعك الرئيسي.

الخيارات الصحيحة:

1. **سجلّ DNS فقط (رمادي)** — وهو المطلوب هنا. لا Proxy، مرور مباشر.
2. نطاقات فرعية لكل نود على سجلّ DNS مباشر.
3. Spectrum (خطة مدفوعة) إن أردت Proxy فعلاً.

لا تضع سجلّاً برتقالياً ثم تنتظر أن يعمل اتصال TCP على منفذ مخصص.

## 4. الجدار الناري

افتح **نطاق المنفذ الخاص بالنود** فقط — لا كل المنافذ:

```sh
# ufw
ufw allow 20000:32000/tcp

# أو nftables
nft add rule inet filter input tcp dport 20000-32000 accept
```

### تحذير مهم حول Docker و UFW

Docker يكتب قواعده في `iptables` **قبل** قواعد `ufw`، وشريط `DOCKER-USER`
يعيد توجيه الحزم مبتعداً عن سلسلة `INPUT`. النتيجة العملية: **قواعد UFW على
`INPUT` قد لا تُطبَّق على حركة المرور المعاد توجيهها من Docker.**

المنصة لا تعيد بناء جدارك الناري ولا تمسّه. هي فقط تُضيف قواعد معزولة داخل
`DOCKER-USER` و `INPUT`، موسومة بـ `troxe:` لكل صندوق رمل على حدة:

```sh
iptables -S DOCKER-USER | grep 'troxe:'   # قواعد عزل كل صندوق
```

هذه القواعد منعزلة ولا تمس قواعدك. للتحقق من سلامتها بعد أي إعادة تشغيل للمضيف:

```sh
curl -s https://api.<domain>/api/v1/admin/nodes -H "Authorization: Bearer $ADMIN_TOKEN" \
  | jq '.[] | {id, firewall}'   # ok: true = كل القواعد موجودة
```

### لا تفتح كل المنافذ

المنصة تحتاج منفذاً واحداً من الـpublic للموقع، وواحداً للـAPI، و`22` لـSSH.
بقية المنفذات تُفتح **فقط** لنطاق نود العملاء.

## 5.Programma التحقق بعد الإعداد

من الـnode نفسه:

```sh
# 1. البورت منشور على الحاوية
docker port srv_<hex>          # يجب: 3000/tcp -> 0.0.0.0:20042

# 2. الخدمة تستمع داخل الحاوية
docker exec srv_<hex> sh -c 'cat /proc/net/tcp | awk "NR>1 && \$4==\"0A\"{print \$2}"'

# 3. البورت المنشور يستجيب من الـnode
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:20042/

# 4. يستجيب عبر العنوان العام
curl -sS -o /dev/null -w '%{http_code}\n' http://node.hosting.troxe.dev:20042/
```

من **شبكة خارجية** (الخطوة الوحيدة التي تُثبت الوصول من الإنترنت):

```sh
# من أي جهاز خارج المضيف
curl -sS -o /dev/null -w '%{http_code}\n' http://node.hosting.troxe.dev:20042/
```

أو خدمة فحص خارجية:

```sh
curl -s -H 'Accept: application/json' \
  "https://check-host.net/check-tcp?host=node.hosting.troxe.dev:20042&max_nodes=4"
```

> لوح��ة التحكم **لا** تعرض الوصول من الإنترنت كحقيقة مؤكدة، بل
> `not verified`. هذه حالة مقصودة: الـnode لا يستطيع قياس مسار يبدأ وينتهي
> داخله. إن أردت عرضها确诊اً، أضف probe خارجي واربطه بالـAPI.

### لماذا فحص TCP البسيط لا يكفي

قياس حقيقي على هذا المضيف:

```
منفذ منشور، لا يوجد مستمع داخل الحاوية  →  connect() ينجح        ← كاذب!
منفذ منشور، هناك مستمع                 →  connect() ينجح ويبقى مفتوحاً
```

بسبب ذلك تستخدم المنصة فحصاً أقوى: تتصل، ثم تتأكد أن الاتصال **ما زال
مفتوحاً** بعد 350ms. الميت يُغلق خلال ~11ms.

```
منفذ ميت   → CLOSED @11ms
منفذ حي    → SURVIVED @502ms
```

هذا ما يميّز «Docker نشر البورت» عن «الخدمة تستمع فعلاً».

## 6. عند إضافة نود جديد

1. **Admin → Nodes → New node**، وضع `public_host` (= عنوان يخدمه العملاء)
2. `Set port range` إن أردت نطاقاً مختلفاً عن افتراضي المنصة
3. على المضيف: شغّل `scripts/node-setup.sh` (يثبّت TLS و supernet وقواعد العزل)
4. **افتح النطاق على جدار المضيف والمزوّد**
5. **سجلّ DNS** يشير إلى العنوان العام
6. `Run health check` من اللوحة — يجب أن يقرأ `firewall: ok`

---

## 7. استكشاف الأعطال

| العرض في اللوحة | السبب المرجّح | الفحص |
|---|---|---|
| `No published port` | لا يوجد تخصيص في قاعدة البيانات | `GET /servers/:id/ports` |
| `Not published` | تخصيص موجود، Docker لم ينشره | `docker port srv_<hex>` |
| `Not listening` | الحاوية تعمل، لا شيء يستمع على `CONTAINER_PORT` | `docker exec … /proc/net/tcp` |
| `Unreachable` | يستمع داخلياً، لكن البورت المنشور لا يرد | `curl 127.0.0.1:<port>` |
| `Reserved` | البورت محجوز لكن الحاوية متوقفة | `docker ps` |
| `Cannot be measured` | نود بعيد — الـAPI لا يصل إلى loopback الخاص به | طبيعي، ليس خطأ |

### تسريب منافذ

إن بقي تخصيص بحالة `allocated` بعد حذف السيرفر، فالسبب أن الحاوية لم تُحذف:

```sql
select server_id, port, reason from server_ports
 where state = 'allocated' and reason is not null;
```

`reason = 'awaiting container removal'` يعني أن المنفذ ما زال مربوطاً. الـ
reconciler يعيد المحاولة كل دقيقة؛ إن استمر، حا��ة أو شبكات بـ`troxe.server-id`
تدل على الحاوية اليتيمة:

```sh
docker ps -a --filter 'label=troxe.managed=true'
```
